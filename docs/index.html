Start

Create a test suite for your own code

  1. Step 1 Score the tests you have qikly --score your_module.pyorqikly --score your_project_folder

    Plants faults in a copy of your code, one at a time, and turns each one your tests did not notice into a question about behaviour nothing checks. Nothing of yours is changed. Where your tests can be

    free, no key

  2. For steps 2 and 3: set one API key, such as GEMINI_API_KEY (Gemini's free tier needs no card; how). For every step, install or upgrade with pip install --upgrade qikly, check your tests pass on their own with python -m pytest, and run from your project's root folder. Each step takes one module or a whole folder, and every step takes the same path. No tests yet? Start at step 2. No code yet? qikly --init makes a blank task file for your answers, and step 3 writes the code.

  3. Step 2 Check the drafted spec qikly --scaffold your_module.pyorqikly --scaffold your_project_folder

    A spec agent reads your README, docs and docstrings, never your code, and writes an answer to each of step 1's questions as acceptance criteria, in inputs_private/config/tasks/YOUR_MODULE_VERIFY.yaml. The answers it had to judge are marked CHECK, and what your docs do not decide is left as a TODO for you. Keep or change any of them, and qikly --validate with the same path checks the file, free.     a fraction of a cent with a key
  4. Step 3 Get a fresh test suite written from your answers qikly --tasks your_module.pyorqikly --tasks your_project_folder

    A test agent writes tests from your answers before any code is shown to it, and a separate coding agent, which never sees them, repairs a copy of your code until they pass. Where your tests can be. Anywhere in your project, such as a tests/ folder or beside your code, in files named test_*.py that import your module. Step 1 finds them; to name them instead, add --score-tests test_folder/.

The core idea

Independent test generation for AI-written code

This is step 3 above, qikly --tasks.

How it works

The coding agent never sees the acceptance criteria

One task file holds the requirements, the interface and the acceptance criteria. The test agent reads all three and writes the integration and system tests before any code exists. The coding agent gets the same file with the criteria cut out, and works from failing tests until the suite passes.

Two obvious objections

"Just use one model for the code and another for the tests." That helps a little. It does not fix the underlying issue: both models still read the same criteria, so the code is still built to the standard it is about to be judged by. Changing who types it does not change what they were shown. qikly removes the criteria from the coding agent's prompt, qikly --explain shows the cut, and a test fails the build if any call site lets a criterion through.

"Doesn't a failing test give the criteria away?" It shows the coding agent that one test, its source and its error, and the test often states the rule it checks. It cannot change a test already written: the integration and system suites exist before any code does, so what the agent learns from a failure can shape the code, never the bar.

FAQ

Good questions, straight answers

Does my code leave my machine?

Not for qikly --score: it runs on your machine and calls no model. The steps that use a model, drafting the spec, writing the tests and repairing the code, send what they need to the provider whose key you set: Gemini, OpenAI or Anthropic. Apart from that, the only network call is a check for a newer release, which you can turn off. The privacy page has the details.

Do I need an API key?

Not to start. qikly --score needs no key. Steps 2 and 3 need one key from Gemini, OpenAI or Anthropic.

What does it cost?

qikly --score is free. With a key, drafting the spec costs a fraction of a cent and a run on one file about a cent. A whole folder can cost a few cents, depending on what is tested. qikly defaults to a cheap model, Gemini 3.5 Flash-Lite, which I have tested extensively and which does this work well.

Does it change my code?

No. --score plants its faults in a temporary copy, and the code and tests a run writes go into outputs/. They reach your source tree only if you copy them there, for example with --take-tests.

What does it test, and what doesn't it?

It tests what a Python module does with its inputs: data transforms and ETL steps, calculations, validation rules, merges and business logic, with integration, system and unit tests in pytest. It is built for self-contained modules in small to mid-sized repositories.

It does not test user interfaces, performance, load, security or any other non-functional property, and it does not run end-to-end tests across services.

It fits most naturally where verification already has to be independent of the people who build the thing: automotive, medical devices, fintech and defence.

Is it open source?

Yes, under the Apache License 2.0.
